### 1.3 Критичні функції та стани

- **Критичні функції:** керування реле, збереження стану, перепідключення до мережі, відновлення після збою.
- **Критичні стани:** OPENING / CLOSING (реле під напругою), ERROR (має утримувати реле OFF до RESET), перші ≈500 мс після будь-якого reset (boot path), запис у NVS, офлайн із заповненим буфером.
- **Безпечний стан:** обидва реле OFF.
- **Зовнішні залежності:** живлення (просадки, перебої), мережа й MQTT-брокер, фізичні датчики.

## 2. Scope & Out of Scope

### 2.1 In scope

| Категорія | Що саме | Як |
|---|---|---|
| **Firmware** | Логіка машини станів, таймери, обробка подій, функціональні вимоги | Wokwi, host-модель |
| **Інтерфейси** | GPIO + переривання, UART CLI (текстовий і JSON), I2C | Serial/CLI, logic analyzer |
| **Протоколи** | Формати повідомлень CLI, I2C-транзакції, обробка помилок, таймаути, retry | VCD + декодер, pytest |
| **Сценарії** | Функціональні сценарії, послідовності дій, граничні випадки | Test Matrix T-01…T-37 |
| **Критичні стани** | Відновлення після збоїв (WDT, brown-out, power cut), втрата зв'язку, некоректні входи, перезавантаження | Fault injection, pytest |

### 2.2 Out of scope (свідомо) і чому

| Не тестуємо | Чому | Що з цим робимо |
|---|---|---|
| **Залізо:** схемотехніка, аналоговий brown-out, поріг BOD, EMI/EMC, ESD | Немає стенда; моделі не відтворюють електрику | Residual RR-02, RR-03; T-39 на регульованому БЖ |
| **Механіка:** привід, інерція, струм двигуна, кріплення лімітерів | Немає приводу | Поза межами firmware QA |
| **Дизайн / UI** | У пристрою немає UI, крім LED / buzzer (їх перевіряємо як outputs) | — |
| **Застосунки верхнього рівня:** бекенд телеметрії, мобільний застосунок | Не входять у прошивку | Перевіряємо лише контракт: ID, лічильники, без дублікатів |
| **Сторонні сервіси:** реальний MQTT-брокер, Wi-Fi стек ESP-IDF, радіо | Мережа емулюється командами `NET DOWN/UP` | Residual RR-04, пілот у реальній мережі |
| **Інтеграція всіх підсистем в одну прошивку** | Її не існує: підсистеми тестовано окремими збірками | Residual RR-01, T-40 |
| **Аналіз вихідного коду** | Умова black-box | Код лише компілювався під host-модель |

Чіткий scope захищає від нескінченного розширення тестів. Out of scope — не «забули», а свідоме обмеження з планом, як його закрити.

## 3. Quality Risks

### 3.1 Quality objectives

1. **Functional safety актуатора:** реле не вмикається без команди, не працює за кінцевим положенням чи довше за таймаут, OPEN і CLOSE ніколи не ввімкнені одночасно.
2. **Recoverability:** після зависання, brown-out, перебою живлення, збою периферії чи мережі пристрій сам повертається в робочий і безпечний стан.
3. **Data integrity:** критичний стан і телеметрія або цілісні, або втрату видно в діагностиці.
4. **Robustness інтерфейсів:** некоректний ввід не перезавантажує пристрій і не змінює стан.
5. **Observability:** reset reason, лічильники й індикація правдиві.
6. **Resource stability:** немає витоку heap, reconnect storm, неправильного сну.

### 3.2 Ризики (Ризик = Ймовірність × Вплив, шкала 3 × 3)

Повна матриця з шкалами, переглядом «до / після» та ланцюгами — [docs/risk-matrix.md](docs/risk-matrix.md).

| ID | Failure mode → Impact | I | P | Ризик | Стратегія мінімізації (тести) |
|---|---|:-:|:-:|:-:|---|

| R02 | Реле вмикається після аварійного reset → несанкціонований рух | 3 | 3 | 🟥 9 | Fault injection WDT / brown-out / RESET, ×10, ×20 (T-06…T-10, T-39) |
| R03 | Перебій живлення під час збереження / пошкодження flash → хибний стан реле | 3 | 3 | 🟥 9 | Обрив після K-го запису, bit-flip (T-11…T-14) |
| R04 | Один NACK на I2C → тихе зависання, втрата керування | 3 | 3 | 🟥 9 | Protocol trace + NACK injection (T-15…T-17, T-40) |
| R06 | Офлайн-телеметрія губиться / дублюється без сліду | 3 | 3 | 🟥 9 | BVA буфера, ID-трасування (T-18…T-22) |

## 4. Test Levels & Types

### 4.1 Тестові рівні

Не кожен ризик потребує всіх рівнів. Рівень обрано за тим, де дефект найдешевше виявити й де його можна довести.

| Рівень | Що перевіряє | Ризики | Приклади з проєкту |
|---|---|---|---|
| **Component / interface checks** | Окремі команди, повідомлення, формати вхідних / вихідних даних | R07, R10, R09 | JSON-рядок на кожну команду; межа 40/41 символ; послідовність backoff у `[NET] retry` |
| **Integration testing** | Взаємодія компонентів і модулів | R04 → R02, R11 → R02 | I2C-драйвер ↔ main loop (heartbeat); буфер ↔ MQTT flush; **план:** I2C hang + WDT + реле (T-40) |
| **System black-box testing** | Уся система з точки зору користувача, без знання реалізації | R01, R05, R08, R12 | Лімітер → реле OFF; таблиця індикації R15; одне натискання = одна команда |
| **Fault injection** | Навмисні збої живлення, таймаути, обриви зв'язку, збої шини | R02, R03, R04, R06 | hang → WDT; обрив після K-го запису NVS; NACK на I2C; `NET DOWN` |
| **Non-functional / reliability** | Стрес, навантаження, витривалість, відновлення | R11, R09, R13 | 10 × STRESS 100 heap trend; 20 змішаних reset; тривалість сну |
| **Automation / regression** | Автоматичний повтор після змін | усі 🟥 | pytest W5 (124), W6 (62), W7 (21) з контролем на еталоні |

**Unit-рівень** не застосовувався: підхід black-box, без доступу до коду. **Acceptance** — це рівень рішення: exit criteria §6.2 + Release Decision.

### 4.2 Типи тестів і техніки

| Тип | Техніки | Де |
|---|---|---|
| Functional | State transition, equivalence partitioning, output verification | W1, W6, W7 |
| Boundary / negative | BVA (speed, timeout, довжина рядка, ємність буфера 7/8/9/12, int32), negative input | W3, W6, W7 |
| Timing | Межі часу (9.9 / 10.0 / >10 с), інтервали retry, тривалість сну | W1, W4, W5 |
| Protocol | Аналіз traces, ACK / NACK, незалежний декодер | W4 |
| Non-functional: reliability / recovery | Fault injection, повтори ×10 / ×20 | W5 |
| Non-functional: stress / memory | Outage 20 с, 5 флапів, STRESS 100, heap trend | W7 |
| Combination | Обидва лімітери; команда + стан; шум + critical operation | W1, W2 |

### 4.3 Підхід до автоматизації

Автоматизуємо там, де перевірки **повторювані й детерміновані** і де без коду їх не виконати: fault injection у точну мілісекунду (вікно між двома записами NVS ≈26 мс), повтори ×10 / ×20, ID-трасування сотень повідомлень, межі CLI.
Не автоматизовано: W1 (ручні сценарії в Wokwi GUI; план — Wokwi CI scenarios, як уже написано для debounce у [wokwi/debounce_scenarios](wokwi/debounce_scenarios/)) і W4 (аналіз VCD — напівавтоматично власним декодером). Деталі — [pytest/README.md](pytest/README.md).

## 5. Test Environment

### 5.1 Середовища та що кожне може довести

| Середовище | Призначення | Інструменти | **Може** довести | **Не може** довести |
|---|---|---|---|---|
| **Wokwi simulation** | Логіка станів, реле, LED, таймінги firmware | Wokwi (Arduino Uno, ESP32), Wokwi CI scenarios | Переходи станів, interlock реле, таймаути | Електрику, дребезг реальних контактів |
| **Serial / CLI** | Взаємодія з пристроєм через послідовний порт | Serial Monitor, pyserial / pty, логи з часовими мітками | Протокол CLI, межі, reset reason, стан у `status` | Те, що не виводиться в Serial |
| **Logic Analyzer + PulseView** | Захоплення й аналіз сигналів і протоколів | wokwi-logic-analyzer (VCD), sigrok-cli / libsigrokdecode (як у PulseView), власний декодер | ACK / NACK, адреси, інтервали retry, стан шини IDLE, тривалість імпульсів на GPIO | Ємність лінії, фронти, підтяжки |
| **Python + pytest** | Автоматизація, генерація даних, повтори, перевірка очікуваних результатів | Python 3.13, pytest 9.1, host-модель ESP32, ASan / UBSan | Логіку recovery, атомарність записів, ID-трасування, тренди алокацій | Реальний brown-out, Wi-Fi стек, фрагментацію heap ESP-IDF |
| **MQTT / network environment** | Публікація, доставка, відмовостійкість | CLI-емуляція `NET DOWN/UP`, лічильники `sent / dropped / duplicates`, message ID | Backoff, буферизацію, дублікати, recovery стану | Реальний брокер, RSSI, roaming, TLS |
| **Real hardware** | Фізична валідація: електрика, продуктивність, надійність | ESP32 DevKit, регульований БЖ, логічний аналізатор, PPK2, MQTT-брокер | Те, чого не можуть моделі | — (у цьому циклі **не використано**) |

**Host-модель ESP32** — це спосіб, яким у W2, W3, W5, W6, W7 доступні Serial/CLI і мережеве середовище без плати. Незмінений `sketch.ino` компілюється разом із моделлю Arduino-ESP32 API: UART 115200 з RX FIFO 256 B, GPIO, Task WDT, NVS у файлі, deep sleep, brown-out як reset, облік heap. Час прискорено ×10, тому 60-секундний сон займає мілісекунди.

### 5.2 Конфігурації, стенди, тестові дані

- **Конфігурації:** кожна збірка ідентифікована (§1.2); еталонні `demo`-збірки — контроль harness; W7 збирається з `-O0 -fno-allocation-dce`, бо на `-O1` компілятор прибирав алокацію, і модель не бачила витік.
- **Тестові дані:** набори BVA (speed −1…257, timeout 0…61, int32-межі, довжини 1…300 / 400 / 1000 / 5000), 500 випадкових байтів для UART, значення DHT22 (−60 °C, 120 %), плани випадкових brown-out (W5 BO04), сценарії Wokwi YAML, message ID 1…1000.
- **Доступи:** тестових акаунтів не потрібно; для пілоту — облікові дані MQTT-брокера.

## 6. Entry / Exit Criteria

### 6.1 Entry criteria

| Критерій | Що перевіряємо | Стан у цьому циклі |
|---|---|---|
| **Firmware build доступний** | Збірка успішна, версію промарковано (назва + sha256), працює базовий функціонал (boot, `status`) | ✅ §1.2 |
| **Requirements / expected behavior визначені** | Актуальні вимоги кожної підсистеми, acceptance criteria, очікувана поведінка на межах (edge cases) | ✅, неоднозначності винесено як питання ([defect-log](bug-reports/defect-log.md#спостереження-які-не-оформлено-як-дефекти-питання-до-вимог)) |
| **Test environment готовий** | Інструменти (Wokwi, LA, pytest, мережева емуляція), сервіси, дані. **Еталонна збірка проходить свій набір тим самим harness** (W5 121/124, W6 62/62, W7 21/21) | ✅ |
| **Known limitations задокументовані** | Список обмежень, щоб не заводити хибні дефекти: модель робить миттєвий brown-out; Wi-Fi емульовано; heap — лише алокації прошивки; підсистеми окремими збірками; немає реальної плати | ✅ §5.1, §8 |
| **Critical interfaces доступні для спостереження** | UART / CLI з часовими мітками, стан GPIO реле, I2C через VCD, лічильники мережі в `STATUS` | ✅ |

**Результат:** команда впевнена, що все готове для ефективного виконання тестів. Якщо smoke (§6.3) не проходить, збірка повертається без повного циклу.

### 6.2 Exit criteria

| Критерій | Ціль | Факт | Статус |
|---|---|---|---|
| **Critical scenarios виконані** | 100 %: увімкнення, основний робочий цикл, передача даних, recovery після помилки | 23 / 23 (T-01…T-22, T-37) | ✅ |
| **Немає відкритих blocker / critical defects** | Blocker 0 · Critical 0 · Major ≤ 2 (поза ризиками безпеки) · Minor ≤ 5 | Blocker **8** · Critical **5** · Major **16** · Minor **6** | ❌ |
| **Regression пройдений** | Regression-набір PASS 3/3 прогони, demo-контроль зелений | Результати стабільні 3/3, але стабільно FAIL | ❌ |
| **Recovery scenarios підтверджені** | Перезавантаження, втрата живлення, втрата зв'язку, збій прошивки, пошкодження даних: пристрій відновлюється, реле OFF | Reset reason і recovery мережі — PASS; реле ON після WDT / brown-out / RESET; I2C fault — hang; NVS — змішаний стан | ❌ |
| **Evidence збережений** | Звіти тестів, логи, traces, скріншоти / графіки, вимірювання для кожного FAIL і критичного PASS | 44 позиції ([Evidence Index](evidence-index.md)) | ✅ |
| **Known risks прийняті або задокументовані** | Кожен residual risk оцінено, прийнято командою або задокументовано для відстеження | RR-01…RR-07 задокументовано 02.11.2026; прийняття PO — очікується | ⏳ |

*Blocker* — Critical-дефект у ризиках безпеки актуатора R01–R04 без обхідного шляху (8 шт.). *Minor* включає Medium (3) і Minor (3). «Все протестовано» — не exit criterion.

### 6.3 Regression Strategy

| Рівень | Що входить | Коли | Тести |
|---|---|---|---|
| **Дим-тест (smoke)** | boot + basic CLI + sensor + MQTT | Кожна збірка, автоматично, < 1 хв | Boot у безпечному стані й відновлення збереженого стану (T-14), `status` / один валідний JSON на команду / читання датчика (T-30), офлайн-буферизація та recovery мережі (T-18) |
| **Критичний regression** | control + data integrity + recovery | Кожна зміна в критичних підсистемах, перед merge | T-01…T-22, T-31, T-37 (усі 🟥-ризики) |
| **Повний regression** | functional + protocol + power + network + stress | Перед кожним release candidate, nightly | Усі 40 рядків Test Matrix: W5 124 + W6 62 + W7 21 кейс, ручний набір W1, trace W4, HW-тести T-38…T-40 |
| **Автоматизація** | Лише там, де перевірки повторювані й детерміновані | Smoke і critical — у CI на кожен push | pytest W5 / W6 / W7; W1 → Wokwi CI (план) |

**Вибір за типом зміни** (regression — не «запустити все»):

| Що змінилося | Що запускаємо першим |
|---|---|
| Network stack, MQTT, буфер | T-18…T-22, T-32, T-37: reconnect, буфер, дублікати, heap — витік знайдено саме тут |
| NVS / формат збереження | T-11…T-14, T-07: reset не має відновлювати небезпечний стан |
| Boot path, ініціалізація GPIO | T-06…T-10: увесь fail-safe після reset |
| I2C-драйвер, периферія | T-15…T-17, T-40 |
| Обробка входів, переривання | T-23…T-26, T-01 (лімітери — теж входи) |
| Парсер CLI | T-27…T-30 |
| Машина станів воріт | T-01…T-05, T-31, T-35 |

**Після fix:** той самий тест, що знайшов дефект, плюс сусідні межі (для буфера: N = 7, 8, 9, 12, 100).

### 6.4 Defect management

- **Обов'язкові поля:** ID, requirement, risk, build (sha256), preconditions, steps, **expected, actual**, impact, severity, reproducibility, evidence, regression after fix.
- **Severity — за наслідком:** Blocker / Critical — небезпечний стан актуатора, втрата контролю чи критичних даних без обхідного шляху або неправдива діагностика, що цю втрату приховує; Major — функцію порушено, є наслідки для даних чи ресурсу; Medium / Minor — індикація, діагностика, зручність.
- **Reproducibility:** ≥ 3 прогони; для нестабільних — частота (BO04: реле ON у 1–4 з 10).
- **Стан:** 35 дефектів — [bug-reports/defect-log.md](bug-reports/defect-log.md); 9 release-blocking — [bug-reports/bug-reports.md](bug-reports/bug-reports.md).

### 7.2 Product bug чи environment / test issue

Перед тим як назвати FAIL дефектом прошивки, перевіряємо по черзі: **test logic → environment → communication → requirement → firmware.**
1. **Test logic:** той самий тест на еталонній прошивці проходить (W5 121/124, W6 62/62, W7 21/21).
2. **Environment:** ASan / UBSan без помилок (W3 — 105 прогонів, W7 — сценарій переповнення); модель не псує пам'ять.
3. **Communication:** повтор посимвольно і пакетом (W3), незалежний декодер I2C (sigrok збігся 1:1).
4. **Requirement:** неоднозначні вимоги не трактуються як дефект, а винесені як питання.
5. **Firmware:** лише після цього — bug report із відтворенням ≥ 3/3.

Той самий ланцюжок працює і для PASS: перехресна перевірка другим harness виявила, що рівний heap у першому прогоні W7 був артефактом збірки моделі (`-O1`).

## 8. Risks / Assumptions / Dependencies

### 8.1 Проєктні ризики (ризики самого тестування)

| Ризик | Вплив на тестування | Мітигація |
|---|---|---|
| Немає реальної плати | Фізичні ефекти не перевірено | Явний Out of scope + HW-тести T-38…T-40 як умова exit |
| Немає інтегрованої збірки | Ланцюги R04 → R02, R11 → R02 не перевірено | Інтеграційний тест T-40 після збирання прошивки |
| Сліпі зони harness (модель) | Хибний PASS (так сталося з heap на `-O1`) | Контроль на еталоні + перехресна перевірка другим harness |
| Неоднозначні вимоги | Суперечки «баг чи фіча» | Питання до вимог окремим списком, а не дефекти |
| Один тестувальник, обмежений час | Неповне покриття низьких ризиків | Пріоритет за матрицею ризиків, автоматизація повторюваного |

### 8.2 Припущення та обмеження

- Вимоги кожної навчальної практики = вимоги відповідної підсистеми продукту.
- Host-модель відтворює Arduino-ESP32 API достатньо для логіки (UART, GPIO, WDT, NVS), але **не** електрику.
- Еталонна `demo`-збірка — референс очікуваної поведінки там, де вимога неоднозначна.
- Wi-Fi / MQTT емулюються командами; реальний брокер не використовувався.

### 8.3 Residual Risks

| ID | Residual risk | Чому лишається | Що потрібно, щоб закрити |
|---|---|---|---|
| RR-01 | Інтеграційні ефекти між підсистемами (I2C hang → WDT → реле ON; витік heap → reset → реле ON) | Інтегрованої прошивки немає | Інтеграційна збірка + T-40 + повтор T-07 у ній |
| RR-02 | Реальний brown-out: поріг BOD, повільна просадка, поведінка реле під час просадки | Модель дає миттєвий reset | T-39 на регульованому БЖ з логічним аналізатором |
| RR-03 | Дребезг реальних контактів і EMI на довгих лініях до кнопок / лімітерів | Модель — синтетичні патерни | Осцилограми реальних кнопок, тест із довгим кабелем |
| RR-04 | Wi-Fi: RSSI, roaming, DHCP, TLS, реальний брокер | Мережа емулюється | Пілот у реальній мережі, логи брокера |
| RR-05 | Heap ESP-IDF, фрагментація, стек FreeRTOS, тривала робота (витік прошивки W7 BUG-04 уже знайдено, але інших джерел модель не бачить) | Модель рахує лише алокації прошивки | T-38 soak 24 год на платі |
| RR-06 | Знос flash при частих записах NVS | Немає тривалих випробувань | Оцінка записів / добу, wear-leveling |
| RR-07 | Продуктове рішення: після POWER_ON / SW reset реле відновлюється в ON (і в еталоні) | Не дефект, а невизначена вимога | Рішення PO: «пам'ятати стан» чи «fail-safe OFF» |

## 9. Ролі та рішення

| Роль | Відповідальність |
|---|---|
| **Product Owner** | Приймає рішення GO / NO-GO / Known Risk, приймає або відхиляє residual risks, вирішує RR-07 |
| **QA (Лахно А.)** | Стратегія, ризики, тести, evidence, рекомендація з обґрунтуванням. QA рекомендує, але не ухвалює реліз |
| **Firmware lead** | Root cause і виправлення, узгодження severity, інтегрована збірка |
| **Hardware engineer** | Стенд і HW-тести T-38…T-40 |

**Рекомендація QA: NO-GO.** Повна аргументація — [docs/release-decision.md](docs/release-decision.md).
Відкриті Critical-дефекти є в **кожному** з чотирьох ризиків безпеки актуатора (R01–R04), і кожен веде до одного наслідку: реле під напругою без команди або без обмеження. Ще два Critical: R06 робить втрату телеметрії невидимою, а R11 (витік heap) за години роботи призведе до reset, після якого реле знову ввімкнеться. Жоден не має експлуатаційного обхідного шляху.
